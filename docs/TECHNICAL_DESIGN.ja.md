## 1. 目的

本プロジェクトは、Wayland 環境の COSMIC Desktop 向けに軽量な動画壁紙マネージャーを提供します。

システムは意図的に以下の 2 つのプロセスに分離されています：

1.  **壁紙デーモン (Wallpaper daemon)**
    -   常時稼働（常駐プロセス）。
    -   Wayland layer-shell サーフェスを所有。
    -   GStreamer による動画再生パイプラインを所有。
    -   軽量な Unix ドメインソケット IPC インターフェースを公開。
    -   GUI ツールキットを一切含まない（フットプリント極小化）。
2.  **設定 GUI (Settings GUI)**
    -   オンデマンドで起動される一時的なクライアント。
    -   `libcosmic` を用いて構築。
    -   IPC 経由でデーモンと通信。
    -   設定適用後はユーザーが自由に終了可能。
    -   設定 GUI を閉じても動画再生は一切中断されず継続。

------------------------------------------------------------------------

## 2. 中核要件

### 必須要件

1.  動画のループ再生を継続して維持すること。
2.  デスクトップ操作（ウィンドウの移動、リサイズ、アプリ起動等）を阻害しないこと。
3.  同一動画内でのループ境界において、黒画面フラッシュ、もたつき、フレーム落ちが発生しないこと。
4.  動画の切り替え時（A ➔ B）に、黒画面やちらつきを発生させないこと。
5.  設定 GUI が閉じられても動画再生が継続すること。
6.  GUI を開かずに CLI から動画の変更、一時停止、再開、停止、ステータス取得が行えること。
7.  COSMIC デスクトップのネイティブな静止画壁紙を破壊・上書きしないこと。
8.  ハードウェアデコード（環境および GStreamer プラグインに応じて NVDEC / VA-API 等）を優先利用し（RTX 3080 / nvh264dec 実機環境にて検証済み）、非対応環境ではソフトウェアデコード（avdec_h264）へ安全にフォールバックすること。
9.  4K 解像度（3840x2160）以下の動画のみを許可し、過大な動画を安全に弾くこと。
10. マルチモニター環境において、各画面が独立して再生・制御できること（全画面適用時はベストエフォート方式）。
11. systemd `--user` サービス（`ExecStart=%h/.local/bin/fluffy daemon`）として起動・再起動・管理できること。

## 4. 非破壊オーバーレイモデル

### 4.1 基本方針

Fluffy は、COSMIC のネイティブ壁紙システム `cosmic-bg` と安全に共存します。

-   `cosmic-bg` は `Layer::Background` に静止画壁紙を描画します。
-   Fluffy は `Layer::Bottom`（パネルやドック、ウィンドウより下で、Background より上）にサーフェスを配置します。
-   ネイティブ壁紙ファイルを置換したり、`cosmic-bg` を kill することは一切ありません。
-   Fluffy が停止または異常終了した場合、サーフェスが Wayland プロトコルにより自動破棄され、元の静止画壁紙が即座にデスクトップ上に現れます。

## 5. プロセス境界とライフサイクル

### 5.1 プロセス分離

``` text
+-----------------------------+       +-----------------------------+
|     fluffy (デーモン)        |       |    fluffy-settings (GUI)    |
|                             |       |                             |
| - 常駐プロセス               |       | - 一時プロセス (オンデマンド)|
| - Wayland 接続保持          |  IPC  | - libcosmic アプリケーション |
| - GStreamer パイプライン所有 | <===> | - ファイルピッカー呼び出し  |
| - メモリ: ~40 MB RSS (Idle) |       | - デーモン状態の閲覧・操作  |
| - バイナリ: 4.7 MB          |       | - 終了しても再生に影響なし  |
+-----------------------------+       +-----------------------------+
```

### 5.2 ライフサイクル管理
- デーモンの推奨起動形態は `systemd --user` (`fluffy.service`)。
- デスクトップ環境のログイン時に自動起動し、セッション終了時に SIGTERM によりクリーンに終了。
- GUI はデスクトップランチャーまたは `fluffy-settings` コマンドから随時起動可能。

## 6. 状態モデル

各出力（モニター）ごとに以下の状態マシンを独立して管理します：

``` text
[Uninitialized]
       |
       v init_output()
    [Stopped] <---------------------+
       |                            |
       | play(video)                | stop()
       v                            |
   [Playing] -----------------------+
     |   ^                          |
     |   | resume()                 |
     |   v                          |
    [Paused] -----------------------+
```

- **Stopped**: サーフェスは存在しますが、再生パイプラインは停止中（背景は透明または直前の維持フレーム）。
- **Playing**: GStreamer パイプラインが `PLAYING` 状態で動作し、EOS 到達時は自動シークでループ。
- **Paused**: パイプラインが `PAUSED` 状態で静止フレームを維持。

## 7. Wayland / レイヤーシェル仕様（実装済みと未実装の区分）

Wayland プロトコルの実装状況は以下の通り明確に区分されます：

### 7.1 実装・検証済み機能
- **プロトコル**: `zwlr_layer_shell_v1`
- **対象レイヤー**: `Layer::Bottom`（デスクトップアイコン・ドック・ウィンドウの下層、`cosmic-bg` の直上）
- **アンカー設定**: 上・下・左・右の全方向アンカー（出力全域を隙間なく被覆）
- **キーボード対話**: `KeyboardInteractivity::None`（一切の入力フォーカスを奪わない）
- **初期バッファ**: 親サーフェスに初期透明バッファ (`Argb8888`) を明示的にアタッチし、GStreamer の `waylandsink` が生成するサブサーフェスをコンポジターに確実にマッピング。
- **動的出力ホットプラグ**: モニターの接続 (`new_output`) および切断 (`output_destroyed`) を検出し、サーフェスと再生パイプラインを動的に生成・破棄。
- **動的解像度・ジオメトリ追従**: `OutputManager` が各画面の論理幅・高さ・スケール倍率・座標 (`OutputGeometry`) を追従。解像度変更時（例: 2560x1440 ➔ 3840x2160）やスケール変更時はサーフェス寸法とレンダー矩形を動的更新し、再生中であればパイプラインを新解像度に合わせて再構成。
- **サーフェススケーリング**: レイヤーサーフェス全面アンカーと `waylandsink` のレンダー矩形設定（`overlay.set_render_rectangle(0, 0, width, height)`）によりモニター全画面へ適切にスケーリング表示。
- **マルチモニター管理**: 各ディスプレイに独立したレイヤーサーフェスと GStreamer パイプラインを割り当て（`1 出力 = 1 サーフェス = 1 パイプライン`）。

### 7.2 未実装 / 将来のプロトコル拡張
- **`wp_viewporter` / `wp_viewport` プロトコルの直接バインド**: 現在の実装では、サブサーフェスのスケーリングと配置は `waylandsink` のレンダー矩形およびコンポジター描画（`cosmic-comp`）に委譲されています。Rust クライアント側での Wayland プロトコル拡張 `wp_viewporter` の直接バインド・ピクセルクロッピング制御は **v1 では未実装** であり、将来のプロトコル拡張課題として管理されています。

## 8. 再生アーキテクチャ

### 8.1 デュアルパイプライン・プリロール切替（実機検証済み）

単一のパイプラインで `set_state(READY)` や URI 変更を行うと、`waylandsink` が一時的にバッファを解放し、デスクトップ壁紙が見える黒画面フラッシュが発生します。

Fluffy では実機検証済みのデュアルパイプライン・プリロール機構を採用しています：

``` text
[現行パイプライン A (PLAYING)] =====> [Wayland レイヤーサーフェス]
                                            ^
1. 新規パイプライン B を生成・プリロール開始     |
2. パイプライン B が PAUSED 状態で準備完了   |
3. パイプライン B を PLAYING へ遷移 =========+ (即座に切り替え)
4. 旧パイプライン A を停止・安全に破棄
```

これにより、切り替え時も 1 フレームの黒画面・ちらつきもなくシームレスに新しい動画へ移行します。

### 8.2 完全シームレス・ループ再生 (`about-to-finish` ギャップレス再生 & クロスフェード前処理)

Fluffy では動画のループ再生時における「黒画面」「もたつき」「カクつき」「視覚的ジャンプ」を完全に排除するため、再生エンジンと前処理パイプラインの 2 層でシームレス化を実現しています。

#### 8.2.1 GStreamer `about-to-finish` 事前プリロール (再生エンジン層)
従来のプレイヤーは動画終端に達して `GST_MESSAGE_EOS` を受けてからシーク（巻き戻し）を発行することが多く、これには「デコーダバッファのフラッシュ（破棄）」と「先頭フレームの再初期化・再プリロール」による数十〜数百 ms の描画停止（スタッター）が伴います。
Fluffy では GStreamer `playbin` の **`about-to-finish`** シグナルにハンドラを接続しています：
1. 動画の終端直前に GStreamer のストリーミングスレッドから `about-to-finish` が発火。
2. 同一動画の URI をキューに事前セット。
3. デコーダや Wayland サーフェスを一切停止・フラッシュすることなく、バックグラウンドで先頭フレームがデコード・プリロールされ、**0フレームの遅延・フレーム欠落なしで次の周回へ継続**。
4. 万一 `about-to-finish` が発火しない特殊環境に対する安全ネットとして、従来の EOS `seek_simple(0)` フォールバックも二重に維持。

#### 8.2.2 FFmpeg `xfade` による末尾・先頭クロスフェード前処理 (映像素材層)
動画自体の終端フレームと先頭フレームの構図・動きが異なっている場合、プレイヤーがいかに遅延ゼロで繋いでも視覚的なジャンプが生じます。
Fluffy ではトランスコード時に **FFmpeg の `xfade` フィルタ** によるループ用クロスフェード処理をサポートしています（`loop_crossfade_ms` 設定）：
1. 動画の末尾 $F$ 秒間（例: 1.0 秒）と、先頭から $(D - F)$ 秒間のメイン部分を分割。
2. 末尾 $F$ 秒を先頭 $F$ 秒の上にフェードインでオーバーラップブレンド。
3. これにより、生成される新動画の「最終フレーム」と「次の開始フレーム」は、元動画の同一タイムスタンプ（$D - F$ 秒地点）として完全に時間的・空間的に一致し、肉眼では継ぎ目が一切識別できない永久連続ループ動画となります。

## 9. IPC 仕様 & ジョブ管理

- **通信媒体**: Unix ドメインソケット (`$XDG_RUNTIME_DIR/fluffy.sock`、フォールバック: `/run/user/<UID>/fluffy.sock`)
- **パーミッション**: `0600` (実行ユーザーのみアクセス可能、起動時に古いデッドソケットを自動掃除)
- **形式**: JSON Lines (改行区切り JSON, 1 リクエスト最大 64 KB)

### 9.1 リクエスト受付時の世代番号モノトニック確保 (Arrival-Time Generation)
非同期動画変換と動画切替の競合を完全に防ぐため、世代番号（`generation`）は「変換完了時」ではなく「**set-video リクエストをデーモンが受け付けた時点**」でインクリメントして確保します (`self.generation += 1`)。
- バックグラウンド変換ジョブには受付時点の世代番号が渡されます。
- 変換完了時に、ジョブの世代番号と現在のコントローラー世代番号を比較します。
- 後から別のリクエストが到着していた場合（`job.generation < self.generation`）、古い要求は **Stale（破棄対象）** と判定され、画面へは一切適用されず破棄されます。これにより古いリクエストが遅れて勝ってしまう問題を完全に排除します。

### 9.2 JobManager による複数ジョブ管理と 8 状態モデル
バックグラウンド動画変換は `JobManager` により、以下の 8 つの明確な状態で追跡されます：
`Queued` ➔ `Probing` ➔ `Transcoding` ➔ `Installing` ➔ `Completed`（または `Failed`, `Cancelled`, `Stale`）
複数の非同期ジョブを `HashMap<JobId, TranscodeJob>` で個別管理するため、1つのジョブが完了しただけで全体が Idle に見えるような誤表示は発生しません。

### 9.3 In-Flight 重複排除 (Deduplication)
CLI や GUI から同一の動画（SHA-256 コンテンツハッシュが一致するファイル）に対して同時に変換要求が発行された場合、同一ハッシュの実行中ジョブ（`Queued`, `Probing`, `Transcoding`, `Installing`）を検出して便乗・再利用します。これにより無駄な外部 `ffprobe` や `ffmpeg` プロセスの重複起動を防止します。

### 9.4 設定 GUI の完全非同期 IPC
`fluffy-settings` はすべての IPC 照会およびコマンド発行を `iced::Task` / ワーカースレッド経由で非同期実行します。デーモン側のトランスコード中や高負荷時にも GUI が一切フリーズせず滑らかに動作します。

## 10. リクエスト / レスポンススキーマ

## 11. 永続ストレージと動画正規化

### 11.1 永続ストレージ構造 (`~/.local/share/fluffy/storage`)
変換済みおよび登録済みの動画ファイルは、OSやキャッシュクリーナーによって勝手に破棄されないよう、一時ディレクトリ（`~/.cache`）ではなく **XDG データディレクトリ内の永続ストレージ** に保存されます：
- **動画ファイル**: `$XDG_DATA_HOME/fluffy/storage/videos/<sha256>.mp4`（既定: `~/.local/share/fluffy/storage/videos/`）
- **メタデータ**: `$XDG_DATA_HOME/fluffy/storage/metadata/<sha256>.json`
- **原子的ファイル生成と整合性**: 一時ファイル (`.tmp.*`) に書き出した後、`fs::rename` によるアトミック移動を実施。動画本体とメタデータ JSON の双方が正常に配置されることを保証し、メタデータ書き込みに失敗した場合は動画一時ファイルをクリーンアップして不完全な残留を防止します。

### 11.2 コンテナ形式検証とダイレクトバイパス条件
動画のバイパス判定では、映像ストリーム情報だけでなく **コンテナ形式（format_name）** を厳格に検証します。
以下の条件を**すべて**満たす場合のみ、トランスコードをバイパスして即時コピー・登録します（変換CPU負荷なし）：
- **コンテナ形式**: MP4 (`format_name` に `mp4` または `mov` を含む)
- **映像コーデック**: H.264 (`h264`, `avc1`)
- **色空間**: `yuv420p`
- **スキャン方式**: プログレッシブ
- **解像度**: 偶数ピクセル幅・高さ、かつ 4K 以下 (3840×2160)
- **フレームレート**: 30 fps 以下
- **音声処理**: プレーヤー側で自動ミュート（`fakesink`）されるため音声トラックの有無を問わずバイパス可能

> **重要:** MKV や WebM 等のコンテナに H.264/yuv420p 映像が入っている場合でも、拡張子だけを `.mp4` に偽装して保存することを防ぐため、必ず `ffmpeg` による MP4 への正規化トランスコードを実施します。

### 11.3 規格外動画の非同期バックグラウンド正規化
HEVC/H.265, AV1, VP9, 60fps超、奇数解像度、非MP4コンテナ等の動画は、初回指定時に自動正規化されます：
- **非同期ワーカースレッド実行**: メインスレッドから切り離されたワーカーで ffmpeg（`libx264`, `yuv420p`, 30fps）変換を実行。
- **黒画面ゼロ保証**: 変換処理中もデーモンのメインスレッド（Wayland イベント処理および GStreamer バスイベント処理）は停止せず、**現在の壁紙（前の動画またはデスクトップ壁紙）が滑らかに再生され続けます**。
- **初回負荷と2回目以降の高速性**: 初回のみ変換計算のため CPU 負荷と所要時間（ファン回転）が発生しますが、一度変換された動画は永続ストレージに保存されるため、**2回目以降はトランスコードなしでスムーズに即座に再生**されます。
- **リアルタイム通知・インジケーター**: `fluffy-settings` では回転するアニメーションと案内が表示され、CLI の `fluffy status` でもジョブ進行状況が確認できます。

## 12. 4K バリデーションポリシー

システムリソース保護のため、入力動画に対して以下の検証ルールを厳格に適用します：
- 最大幅: **3840 ピクセル**
- 最大高さ: **2160 ピクセル**
- 5K や 8K などの過大な動画ファイルは、トランスコード前に即座にエラーとして弾かれます。

------------------------------------------------------------------------

## 13. マルチモニターポリシーと全画面適用のベストエフォート仕様

- 接続されている各ディスプレイ（`DP-1`, `DP-2`, `HDMI-A-1` 等）を自動検出。
- ディスプレイごとに独立したサーフェスと再生パイプラインを割り当て。
- `fluffy set-video <PATH>` で全モニター同時適用。
- `fluffy set-video <PATH> --output DP-2` で特定モニターのみ個別適用。
- **ベストエフォート（Best-Effort）適用**: 全画面適用時に DP-1 は成功したが DP-2 でパイプラインエラー等が発生した場合、DP-1 は新しい動画を再生し、DP-2 は以前の状態を維持します。IPC レスポンスには各画面の成否情報（`SetVideoResult` の `outputs: Vec<OutputApplyResult>`）が含まれます（GStreamer パイプラインにおける複雑で不安定なトランザクションロールバックは回避）。
- 画面のホットプラグ（接続・切断）イベントを自動追従。

## 14. 性能目標と測定結果

実機（NVIDIA RTX 3080, COSMIC Desktop, デュアル 1440p）における実測結果：

## 17. エラー処理

エラーカテゴリ：
- `WaylandError`: ディスプレイ接続やサーフェス生成の失敗
- `PlaybackError`: GStreamer パイプライン構築や再生エラー
- `IpcError`: ソケット通信、シリアライズ、古い世代番号の拒否
- `CacheError`: キャッシュディレクトリのアクセス権やファイル破損

## 24. ロギングおよびエラーハンドリング方針

常駐デーモンの長期安定稼働と障害診断の迅速化のため、以下の診断およびエラー処理基準を全モジュールおよび今後追加するコードで遵守します：

### 24.1 `tracing` による構造化ログの統一
* **デーモン・ライブラリ層**: 常駐デーモン、再生、キャッシュ、Wayland、IPC サーバモジュールでは **`println!` / `eprintln!` の直接使用を禁止** し、すべて `tracing::*` (`info!`, `warn!`, `error!`, `debug!`, `trace!`) へ統一します。
* **標準出力は対話的 CLI のみ**: 人間向けの端末コマンド（`fluffy status`, `fluffy import` 等の CLI サブコマンド）のみが標準出力を使用します。
* **イベントレベル規約**:
  * `info!`: ライフサイクル重要イベント（起動、終了、動画インポート、キャッシュヒット/保存、動画適用、出力増減）。
  * `warn!`: 復旧可能な問題（stale generation 破棄、残留ソケット破棄の失敗、コンポジタによるサーフェス破棄）。
  * `error!`: 即時診断が必要な障害（ffprobe 失敗、ffmpeg トランスコード失敗、GStreamer バスエラー）。
  * `debug!` / `trace!`: 詳細プロトコル情報（IPC リクエスト着信、プリロール完了、無害な一時ファイル削除エラー）。

### 24.2 診断コンテキスト（Structured Fields）
ログには可能な限り診断コンテキストを含めます：
* `operation`: 例 `"pipeline_switch"`, `"ffmpeg_transcode"`, `"cache_lookup"`, `"job_complete"`
* 識別子: `output = %name`, `generation`, `job_id`, `client_id = client_id.0`
* ユーザーの長い絶対パスを本文内に冗長に大量出力せず、構造化キー（`path = ?path` 等）を使用します。

### 24.3 エラー伝播と握りつぶしの禁止
* ファイルシステム変更、パイプライン状態遷移、IPC レスポンス送信において、理由のない `let _ = ...` による無言のエラー無視は禁止します。
* 安全に無視可能な後処理（切断済みクライアントへのレスポンス送信失敗や一時ファイルクリーンアップ等）は、`debug!` や `trace!` でコンテキスト付きで記録するか、理由をコードコメントに残します。

### 24.4 GUI の堅牢性
* 設定 GUI (`fluffy-settings`) はデーモンの停止やタイムアウトによって決してパニック（`unwrap`）せず、以下の状態に分類してユーザーに分かりやすく UI に反映します：
  * `connection unavailable`（接続不可）
  * `timeout`（タイムアウト）
  * `daemon stopped`（デーモン停止）
  * `invalid response`（無効なレスポンス）

## 25. アーキテクチャ最適化 & 全画面検知 (Phase 8 改善)

### 25.1 全画面自動一時停止アーキテクチャ（デュアル Wayland プロトコル）
ウィンドウ全画面表示中の GPU/CPU リソース節約のため、Wayland toplevel プロトコルを監視し動画パイプラインを自動で PAUSED / PLAYING へ切り替えます。
* **COSMIC Desktop ネイティブ**: `zcosmic_toplevel_info_v1`（`cosmic-protocols`）をバインドし、各ウィンドウの `state` イベント（Fullscreen = 3）を追跡。
* **wlroots / Sway / Hyprland**: `zwlr_foreign_toplevel_manager_v1`（`wayland-protocols-wlr`）へフォールバックして同等の全画面状態を追跡。
* **事前判定**: Wayland レジストリバインド時にコンポジターの広告するグローバルを走査し、対応可否フラグ `supports_fullscreen_detection` を確定。IPC 経由で設定 GUI へ通知。
* **GUI 連携**: 設定アプリ上で `🟢 コンポジター対応` または `⚠️ コンポジター非対応` を明示表示し、非対応時はトグルスイッチを無効化（disabled）。

### 25.2 動的適応型スリープ（Adaptive Loop Sleep）
常時 5ms の高頻度スリープによる CPU 浪費を解消するため、デーモンの稼働状態に応じた適応型スリープを採用：
* バックグラウンド動画変換中: **5 ms**（プロセスポーリング・進捗優先）
* 通常動画再生中: **16 ms**（約 60fps 周期のイベント処理）
* 完全アイドル待機時: **50 ms**（CPU 使用率 0.1% 未満への低減）

### 25.3 先行トランスコードジョブの即時アトミックキャンセル
ユーザーが連続して壁紙変更を要求した場合、先行する古いトランスコード処理が無駄に CPU/GPU を占有するのを防ぐため、即時キャンセル機構を導入：
* `JobManager::cancel_superseded_jobs` により、同一ディスプレイ向けの旧ジョブを検出。
* `Arc<AtomicBool>` によるキャンセルトークンを保持し、即座に `child.kill()` を発行して ffmpeg プロセスを強制終了・一時ファイルをクリーンアップ。

### 25.4 適合動画のハードリンク高速インポート
規格適合（H.264/30fps以下/yuv420p/偶数解像度）動画のキャッシュインポート時、同一ファイルシステム内であれば `fs::hard_link` を試行。ディスク I/O と容量消費をゼロに抑えて瞬時に登録（クロスデバイス時は `copy` へ安全にフォールバック）。

### 25.5 安全性向上とメモリ保護
* **NULL チェック**: `gst_wl_display_handle_context_new` の戻り値 NULL 検証を追加し、初期化失敗時のセグメンテーション違反を未然に防止。
* **バッファ容量動的再計算**: ディスプレイの解像度変更（ホットプラグやスケール変更）時、共有メモリ `SlotPool` のバッファ容量を新しいジオメトリに基づき動的に再計算・再割り当てし、バッファオーバーフローを防止。
* **Safe POSIX**: `libc::getuid` による不安全な FFI 呼び出しを、安全な Rust 製インターフェース `rustix::process::getuid()` に置換。
* **宣言型 CLI**: 手動の引数文字列分割ロジック（約 150 行）を型安全な `clap` derive マクロへ移行。
