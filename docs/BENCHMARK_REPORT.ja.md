## 3. 実機観察とアーキテクチャ検証結果

1. **切り替え過渡期の CPU スパイクゼロ (追加 CPU 負荷 0〜2% 程度)**:
   - 一般的な動画壁紙アプリでは、動画切り替え時に CPU ソフトウェアブレンド（ARGB 変換やメモリコピー）を行うため CPU が 100% 近くまでスパイクし、デスクトップ UI のカクつき（スタッター）を招きます。
   - Fluffy では Wayland プロトコル **`wp_alpha_modifier_v1`** を採用。デコードされた DMABuf バッファを CPU メモリにコピーすることなく、そのままコンポジターへ転送するため、4K デュアル再生のクロスフェード中であっても **CPU 負荷の増加はわずか +2.2%（1080p では +0.1%）** に抑えられます。
2. **コンポジター GPU (3D) シェーダーによる完全オフロード**:
   - アルファ透過合成は `cosmic-comp`（GPU コンポジター）の描画シェーダーで行われます。過渡期に GPU 3D 利用率が一時的に上昇（1080p で 24.6% ➔ 41.9%、4K で 26.9% ➔ 55.5%）していることは、透過ブレンディング処理が GPU へ完全にオフロードされている直接のエビデンスです。
3. **過渡期メモリの即時・完全解放 (Zero Memory Leak)**:
   - 4K デュアル画面での切り替え中、2本のパイプラインを一時並行稼働させるため RSS メモリが一時的に約 900MB 増加（2,111MB ➔ 3,011MB）しますが、3.0秒のフェード終了と同時に旧パイプラインが `Null` 破棄され、**2,048MB（開始前と同等以下）へと即座に 100% 回収**されることを確認しました。
4. **黒画面・ハードカットの完全防止（2重サブサーフェス同期）**:
   - GStreamer `waylandsink` が生成する親 `area_surface`（黒背景・余白）と子 `video_surface`（動画）の両方に動的にアルファモディファイアをバインドし同期制御することで、初回描画時の黒画面ハードカットを一切発生させず、真のディゾルブ推移を達成しています。
5. **120Hz/60fps スムーズステップ（Cubic Easing）ペーシング**:
   - 8ms 周期（120Hz）のスムーズステップ（$3x^2 - 2x^3$）アニメーションにより、途切れやカクつきのない極めて滑らかなクロスフェードを実現しています。
6. **バイナリサイズと常駐フットプリント**:
   - 常駐デーモンのバイナリサイズはわずか **4.7 MB**（strip後 **3.3 MB**）であり、`libcosmic` GUI 依存を分離して軽量なバックグラウンドフットプリントを維持するという基本設計方針を完璧に達成しています。
7. **初回正規化変換と2回目以降の再生特性**:
   - **適合規格動画 (MP4 コンテナ + H.264/yuv420p/30fps)**: トランスコード処理を完全にバイパスし、即時（0.1 秒未満）に永続ストレージへ配置されて再生開始します（CPU 負荷スパイクなし）。
   - **規格外動画 (HEVC/60fps/MKV等) の初回処理**: 初回指定時のみ ffmpeg による H.264/30fps 変換が非同期ワーカースレッドで実行されるため、変換中も既存の壁紙は途切れることなく再生され続け、黒画面は発生しません。
   - **2回目以降の再生**: 永続ストレージ (`~/.local/share/fluffy/storage`) に保存された動画が即座に再利用されるため、CPU 負荷スパイク・ファン騒音・待ち時間ゼロでスムーズに再生されます。
